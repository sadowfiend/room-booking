# Бронирование переговорной

Тестовое задание: интерфейс бронирования одной переговорной комнаты в течение рабочего дня (09:00–18:00).
Пользователь выбирает дату, смотрит брони на неё, создаёт, редактирует и удаляет бронь.
Next.js 16 (App Router), React 19, TypeScript, Tailwind v4; mock API на Route Handlers, хранилище — Redis (Upstash) или память.

**Деплой:** https://room-booking-two-delta.vercel.app — хранилище Redis: `/api/health` на проде возвращает
`{"ok":true,"storage":"redis"}`.

ТЗ — [`SPEC.md`](SPEC.md) (с разделом Open questions), план и принятые решения — [`PLAN.md`](PLAN.md).

## Запуск

```bash
nvm use            # Node 22 (.nvmrc); нужен Node >= 20.19
npm ci
npm run dev        # http://localhost:3000
```

Проверки: `npm run typecheck && npm run lint && npm test`, сборка — `npm run build`.
Сейчас 500 тестов зелёные; ещё 22 теста гоняются на настоящем Redis и без `REDIS_TEST=1` пропускаются.

Переменные окружения — в [`.env.example`](.env.example), все необязательные:

| Переменная | Назначение |
|---|---|
| `UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN` | Redis (Upstash напрямую) |
| `KV_REST_API_URL` + `KV_REST_API_TOKEN` | Redis через Vercel Marketplace; поддерживается и вариант с префиксом `<PREFIX>_KV_REST_API_*` |
| `NEXT_PUBLIC_ROOM_TZ` | часовой пояс комнаты, по умолчанию `Asia/Bishkek` |
| `MOCK_ALLOW_FORCED_CONFLICT=1` | сервер принимает заголовок принудительного конфликта |
| `NEXT_PUBLIC_DEV_TOOLS=1` | в форме виден переключатель «Инструмент разработчика» |
| `REDIS_TEST=1` | включает тесты репозитория на настоящем Redis |

Без переменных Redis сервер хранит брони в памяти процесса. `GET /api/health` показывает текущее хранилище: `memory` или `redis`.

## Архитектура

Зависимости идут только сверху вниз:

```
src/domain/booking   правила, типы, время, тексты ошибок — чистые функции, «сейчас» передаётся параметром
src/server           репозиторий (память / Redis) и сервис: разбор → 404 → 422 → 409
src/app/api          тонкие route handlers: разбор запроса и перевод ошибок сервиса в HTTP
src/lib/api          клиент: единственное место с fetch и HTTP-статусами, наружу — типизированные ошибки
src/features/booking UI: правила — только через domain, сеть — только через lib/api
```

**Одна точка правил.** Форма и сервер вызывают одни и те же функции домена: `parseBookingInput` (формат),
`validateBooking` (правила 1–4, 6, шаг, идущие брони), `findConflicts` (5, 7) и `getSlotAvailability`
(доступность вариантов в форме). Тексты ошибок есть только в `messages.ts`, остальной код работает с кодами.
Форма подсказывает заранее, но последнее слово за сервером.

## Что сделано

- **Правила 1–7 из ТЗ.** Рабочий день, `start < end`, 30–120 минут, полуоткрытые интервалы (касание границ не конфликт),
  запрет прошлого (прошедшие даты; на сегодня — слоты раньше «сейчас»), исключение самой брони при редактировании.
- **Правило 8.** Конфликт от сервера (409) — ожидаемая ситуация. Форма остаётся открытой, введённые данные
  сохраняются, баннер перечисляет конфликтующие брони и получает фокус, список перезагружается.
- **404** при изменении или удалении брони, удалённой в другой вкладке: сообщение и перезагрузка списка.
- **Состояния UI:** загрузка (скелетон), пусто, ошибка с «Повторить», фоновое обновление без очистки списка,
  отправка формы (`aria-busy`). Ответ на старую дату не перезаписывает новую (`AbortController`).
- **Выбор времени** — два нативных `<select>` по 36 вариантов. Недоступные варианты отключены, причина
  («занято», «прошло», …) видна прямо в тексте варианта.
- **Доступность и адаптивность:** подписи у полей, `role=status` / `role=alert`, видимый фокус, управление с клавиатуры, вёрстка от 360px.
- **Redis с CAS** — чтобы бронь была видна с другого устройства, см. «Допущения и компромиссы».
- **Редизайн UI** (PLAN.md, фаза 4.5, этапы 1 и 2): цветовые токены и тёмная тема по `prefers-color-scheme`,
  карточки броней, скелетон без анимации при `prefers-reduced-motion`, пустое состояние; кнопки даты
  «‹ Сегодня Завтра ›», декоративная полоса дня (`aria-hidden`), управление фокусом (подтверждение удаления,
  Esc, возврат на «Новая бронь» после сохранения), подсветка конфликтующих карточек при 409.
  Ширины 360, 390, 768 и 1280 px проверены вручную.
  - **Известное ограничение:** в Safari после «Отмена» или Esc в подтверждении удаления фокус не возвращается
    на кнопку «Удалить бронь …» — Safari не фокусирует кнопку по клику. Способ исправления записан в PLAN.md (фаза 4.5).
- **Интеграция:** API на собранном приложении проверено 23 запросами — [`docs/manual-qa.md`](docs/manual-qa.md).

## Допущения и компромиссы

- **Часовой пояс — `Asia/Bishkek`** (меняется через `NEXT_PUBLIC_ROOM_TZ`). «Прошлое» и «сейчас» считаются в поясе
  комнаты, а не браузера или сервера. «Сейчас» вычисляется только на клиенте.
- **Шаг 15 минут** — по ответу заказчика; одна константа `SLOT_STEP_MINUTES`.
- **Идущие брони можно редактировать и удалять** (в ТЗ этого нет). Исходный `start` можно оставить, новый `start`
  должен быть не раньше «сейчас», `end` — позже «сейчас». Прошедшие брони — только для просмотра.
- **PATCH принимает полное тело** `{ date, start, end, title? }`, как PUT, без слияния с исходной бронью.
  Перенос на другую дату разрешён.
- **Ложный 409 при высокой конкуренции.** Запись в Redis — оптимистическая блокировка по версии даты. Сервер читает
  брони и версию, проверяет пересечения доменной функцией, а Lua-скрипт записывает, только если версия не изменилась.
  После 3 неудачных повторов возвращается 409, даже если реального пересечения нет. Для одной комнаты это приемлемо:
  правило пересечений не дублируется в Lua, нет замков с TTL, UI обрабатывает 409 без потери ввода.
- **Хранилище в памяти без env:** на serverless данные не общие между инстансами и теряются при перезапуске.
- **Без zod.** Проверка тела запроса — около 30 строк `parseBookingInput`, которая возвращает те же коды ошибок,
  что и `validateBooking`. Контракт ошибок описан в одном месте, второго языка схем нет.
- **Без TanStack Query.** Нужны три вещи: состояние загрузки, перезагрузка после мутации или 409, отмена
  устаревшего запроса. Это небольшой хук `useBookings` с `AbortController`. Мы отказываемся от кеша между датами,
  дедупликации и обновления при возврате на вкладку — для четырёх эндпоинтов они не нужны.

## Как показать 409

- **Через UI:** задайте `NEXT_PUBLIC_DEV_TOOLS=1` (до `npm run build`, переменная встраивается при сборке)
  и `MOCK_ALLOW_FORCED_CONFLICT=1`. Включите в форме «Инструмент разработчика: следующее сохранение вернёт 409» и сохраните
  свободный слот: сервер вернёт 409, ввод сохранится, список обновится.
- **Через API:** при `MOCK_ALLOW_FORCED_CONFLICT=1` любой `POST` или `PATCH` с заголовком `x-mock-force-conflict: 1`
  получает 409. Без этой переменной заголовок игнорируется.
- **Настоящий конфликт:** создайте бронь в одной вкладке, а в другой, не обновляя список, отправьте пересекающуюся.

## Как я работал с AI

Работа шла в Claude Code. Основная сессия (Opus) планировала, проверяла и коммитила; код и тесты писали агенты
из `.claude/agents`:

| Агент | Модель | Роль |
|---|---|---|
| `planner` | Opus | декомпозиция фаз, варианты решений; кода не пишет |
| `implementer` | Sonnet | код строго в перечисленных файлах |
| `test-writer` | Sonnet | тесты по ТЗ и контракту, а не по реализации; правит только `*.test.*` |
| `scout` | Haiku | поиск по коду |
| `reviewer` | Opus | ревью в чистом контексте (не запускался) |

- Каждый отчёт агента основная сессия перепроверяла сама: читала код, запускала typecheck, lint и test.
  Коммит — только после зелёных проверок и моего «ок» на `git diff --stat`.
- Сервер и UI делались параллельно, в отдельных `git worktree` (`feat/server`, `feat/ui`), каждый в своей сессии,
  затем слиты локально в `main`.
- Расход — в [`docs/ai-usage.md`](docs/ai-usage.md): проценты лимита из `/usage` (подписка не показывает токены и $),
  токены — из отчётов агентов.
- Переписки: [`docs/ai-chats/INDEX.md`](docs/ai-chats/INDEX.md), сжатые версии —
  [`01-planning-digest.md`](docs/ai-chats/01-planning-digest.md) и [`02-implementation-digest.md`](docs/ai-chats/02-implementation-digest.md).

Эпизоды, которые стоит знать:
- **Агенты не загрузились в первой сессии**, задачу 1.1 выполнил `general-purpose`. После этого правило: агенты
  вызываются только по имени; если агент не запускается — остановка, без подмены.
- **«Файлы уже существовали».** Implementer написал так в отчёте. Основная сессия по времени изменения файлов сочла
  это ложью — это был мой неверный вывод. По логам оказалось, что вторая сессия, параллельно запущенная в том же
  рабочем дереве, на минуту раньше создала эти файлы своим implementer. Агент был прав. Исправлено по логам.
  Урок: одна сессия — одно рабочее дерево, а выводы о нарушениях сверять с логами всех сессий.
- **PR #1** сначала был записан как самовольный — тоже неверно: по логам push и PR сделаны по моей просьбе.
  PR не мерджился через GitHub, ветку слили локально.
- **`.env.example` под запретом прав.** Агент 3C не смог прочитать и изменить файл из-за правила в настройках,
  обходить его не стал и вынес вопрос. Файл я добавил сам, основная сессия закоммитила его без чтения содержимого.
- **`LayoutProps` в свежем worktree.** typecheck падал, потому что в новом worktree не было сгенерированных типов
  Next. Implementer UI остановился (файл вне его списка) — в скрипт `typecheck` добавлен `next typegen`.
