# Работа с AI: сжатая хронология

Сжатая хронология работы с Claude Code над тестовым заданием. Полный лог первой сессии лежит в `docs/ai-chats/01-planning.txt`,
расход по фазам — в `docs/ai-usage.md`.
Схема работы: основная сессия (Opus) координирует, проверяет и коммитит. Код пишет `implementer` (Sonnet),
тесты по SPEC и контракту — `test-writer` (Sonnet), поиск по коду — `scout` (Haiku), планы — `planner` (Opus).
Каждый отчёт агента основная сессия перепроверяла сама: читала код и запускала `typecheck`, `lint` и `test`.

## Фаза 0. Подготовка (предыдущая сессия)
- **Запрос:** настроить тестовую инфраструктуру, документы (PLAN, CLAUDE, SPEC Open questions) и агентов.
- **Сделано:** Vitest (по умолчанию node, jsdom только по директиве в файле), alias `@/*`, Node 22, коммит `chore(setup)`.
- **Ошибка:** агенты из `.claude/agents` в той сессии не загрузились, и задачу 1.1 выполнил `general-purpose`.
  **Вывод:** с этого момента агенты вызываются строго по имени. Если агент не запускается, сессия останавливается
  и сообщает об этом, а не подменяет его другим.

## Фаза 1. Домен
**1.1 Конфиг, типы, время** (`general-purpose`, предыдущая сессия). Чистые функции; «сейчас» передаётся параметром;
часовой пояс комнаты `Asia/Bishkek` с откатом на него при неверном значении. Ручные проверки 1.1 не выбросили,
а перенесли в 1.3 как обязательные случаи: 18:00 UTC → следующая дата, 2026-02-30 и 2028-02-29, число слотов, неверный TZ.

**1.2 Правила** (`implementer`, Sonnet)
- **Контракт пользователя:**
  - `validateBooking` отвечает за правила 1–4, 6 и за идущие брони;
  - `findConflicts` — за правила 5 и 7 (полуоткрытые интервалы, исключение самой брони);
  - сервер сначала проверяет данные (422), потом пересечения (409).
- **Пробел в контракте:** для времени не по шагу не было кода ошибки. Временно использовали `INVALID_TIME`
  и вынесли это пользователю как вопрос.
- **Ошибка основной сессии (исправлено по логам):** агент написал, что файлы «уже существовали»; сессия объявила это ложью
  по времени изменения. Логи показали: параллельная сессия (`session-1`) в том же дереве на минуту раньше создала их своим implementer. Агент был прав.
- **Проверка основной сессии** по правилам 1–7 SPEC: блокирующих ошибок нет, найдено 5 замечаний. Пользователь принял:
  - отдельный код `OFF_STEP`;
  - не показывать `END_IN_PAST`, если уже есть `START_IN_PAST`;
  - убрать лишнее сравнение;
  - PATCH принимает полное тело, как PUT;
  - инвариант «сервис всегда разбирает тело до валидации».

**1.3 Тесты домена** (`test-writer`, Sonnet). 97 тестов, ошибок в реализации не найдено. Агент сам исправил
два своих неверных входных значения. Основная сессия проверила, что ожидания при этом не подогнаны под реализацию.
- **Отклонено пользователем:** тесты закрепляли двойные ошибки («не по шагу» вместе с «слишком коротко»), это шум в форме.
  Решение: если время не по шагу, длительность не проверяется. Implementer поправил правило, test-writer — тесты.

**1.4 Доступность слотов** (`implementer` → `test-writer`)
- Пользователь спросил, откуда взялась `getSlotAvailability`. Ответ: её контракт был в PLAN 1.2, но прошлая сессия
  вынесла файл «отдельной задачей» и саму задачу не завела. Пробел закрыт задачей 1.4.
- Функция возвращает по каждой ячейке «свободно», «прошло» или «занято» и правил заново не реализует: внутри
  вызываются `validateBooking` и `findConflicts`.
- **Итог:** коммит `feat(domain)`, 108 тестов, typecheck и lint зелёные.

**Изменение требований: шаг 15 минут** (ответ заказчика). Implementer поменял одну константу и подтвердил, что
больше нигде шаг числом не зашит. Test-writer обновил тесты: 37 точек, 36 ячеек, 45 минут допустимо. Итог: 143 теста, коммит.

## Фаза 2. Клиент API (`implementer` → `test-writer`)
- До запуска основная сессия дописала в PLAN тела успешных ответов, 204 для DELETE, код `UNKNOWN` и проброс отмены
  запроса. Так серверная и UI-ветка не могли бы понять контракт по-разному.
- **Результат:** типизированные ошибки по статусам, `fetch` и HTTP-статусы есть только в `src/lib/api`.
  33 теста с подменённым `fetch`, всего 141, коммит `feat(api-client)`.
- **Замечание основной сессии:** если запрос отменяют во время чтения тела, приходит `UNKNOWN`. Принято как правило
  для UI: перед обработкой ошибки проверять `signal.aborted`.

## Изменения требований перед фазой 3
- **Заказчик:** проверка будет с нескольких устройств. Redis перешёл из опциональной фазы 7 в обязательную задачу 3C.
- **Атомарность:** предложены три варианта, принят CAS по версии даты.
  - Сервер читает брони и версию, проверяет пересечения доменной функцией, Lua-скрипт записывает только при совпадении
    версии. Этот вариант принят: правило пересечений не дублируется на Lua.
  - Блокировка на дату отклонена: нужен TTL, и замок может «зависнуть».
  - `WATCH/MULTI` отклонён: HTTP-клиент Upstash не держит соединение.
  - **Осознанный компромисс** (README, PLAN): после трёх неудачных повторов возможен ложный 409.
- **Зависимость:** `@upstash/redis` пользователь разрешил явно, как обычную, а не dev-зависимость, и только в 3C.
  Имена переменных окружения берутся из списка допустимых пар (Upstash напрямую, Vercel Marketplace, свой префикс),
  а не одним жёстко зашитым именем.
- Репозиторий асинхронный с первого дня, проверка и запись — одна атомарная операция. Поэтому Redis подключился без правки сервиса.
- **UI:** выбор времени — два нативных `<select>` по 36 значений, а не сетка кнопок.

## Фаза 3. Сервер и UI (две параллельные сессии в отдельных worktree; промпты подготовила основная сессия)
- **3A Сервер и 3C Redis** (`feat/server`, implementer → test-writer):
  - async-репозиторий, сервис, тонкие route handlers;
  - CAS по версии, выбор хранилища по env, `/api/health`;
  - 343 теста плюс 22 теста на настоящем Redis, которые пропускаются без `REDIS_TEST=1`.
- **3B UI** (`feat/ui`, implementer → test-writer): список, форма, обработка 409 и 404 без потери ввода. 243 теста в ветке.
- **PR #1 (исправлено по логам):** считался самовольным, но в `session-7` пользователь сам попросил «запушь feat/ui» и
  «создай PR в main». PR не мерджили через GitHub, ветку слили локально.

## Фаза 4. Интеграция (основная сессия, `scout` на Haiku)
- `feat/server`, затем `feat/ui` слиты в `main` через `--no-ff`. Ожидались конфликты в 4 файлах, но обе ветки правили
  только `package.json`, и в разных строках. Git свёл его сам, результат проверен вручную.
- **Проверки:** после каждого слияния typecheck, lint и test зелёные. Итог: 443 теста и 22 пропущенных.
  Это не 343 + 243: 143 общих теста домена и клиента входили в счёт обеих веток.
- `.env.example` добавлен в индекс без чтения содержимого, как просил пользователь.
- `npm run build`: `/api/bookings`, `/api/bookings/[id]` и `/api/health` динамические.
- `docs/manual-qa.md` — 12 сценариев со ссылками на тесты. `scout` сопоставил сценарии с тестами, основная сессия
  сверила ссылки выборочно. На собранном приложении прогнаны 23 API-проверки, все совпали с ожидаемыми:
  касание границ, 409, 422, 404 после удаления, гонка «1 × 201 и 9 × 409». Проверки в браузере и со второго
  устройства оставлены человеку.

## Фаза 4.5. План редизайна UI (`planner`, Opus)
- **Запрос:** «красивый и дружелюбный» UI, менять только слой представления, все 443 теста должны остаться зелёными.
- **Сбой инструментов:** проверка разрешений auto mode несколько раз не вынесла решения. Сессия не подменила planner
  другим агентом и остановилась. После переключения пользователем на ручной режим planner запустился.
- **Предложение planner:**
  - A «Спокойные карточки» (список и декоративная полоса дня) — **принято**;
  - B «Вертикальное расписание» — **отклонено**: основной список превращается в шкалу (противоречит решению
    про `<select>`), ломаются тесты и масштаб 200%, появляется поведение, которого нет в SPEC.
- **Ответы пользователя:** `addDays` в слое UI (домен не трогаем); тёмная тема только по системной настройке; без подстановки времени по клику.
- В PLAN записаны два этапа (оформление; навигация и фокус) и чек-лист ролей, подписей и текстов, на которые опираются тесты.
- Коммит `docs(plan)`. Реализация отложена до сброса лимита сессии.

## Оформление переписок (основная сессия)
- **Запрос:** сжатые версии и экспорт логов сессий (`session-*-full.md`) в `docs/ai-chats/`.
- **Проверка секретов до коммита:** grep выводил только файл и номер строки, значения проверялись по длине без печати.
  Найдены только имена переменных и уже замаскированные значения; в истории git токенов нет. Коммит и push — по ок пользователя.
