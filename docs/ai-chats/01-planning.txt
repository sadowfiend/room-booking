  1. Как я понял задачу

  Одна переговорка, рабочий день 09:00–18:00. Нужен CRUD броней по дням: выбрать
  дату, увидеть брони, создать, отредактировать, удалить. Сервер — mock на
  Route Handlers. Он сам проверяет бизнес-правила и отвечает 409, если брони
  пересекаются. UI должен корректно обрабатывать 409: показать понятное
  сообщение, перезагрузить список и не потерять то, что ввёл пользователь.
  Оценивают не дизайн, а аккуратность: состояния UI, разделение слоёв, читаемый
  TypeScript.

  Неоднозначности и что я предлагаю по умолчанию:

  - Шаг времени. 15 минут. Минимум 30 минут кратен шагу, а лишних вариантов в
    выборе немного. Шаг задаётся одной константой.
  - title. Необязательный, как в типе Booking. Пробелы по краям обрезаются,
    длина до 100 символов. Пустая строка превращается в «нет title».
  - Часовой пояс для «прошлого». Это главная ловушка: на Vercel сервер работает
    в UTC. Предлагаю один часовой пояс комнаты, заданный константой или env
    (например, Europe/Moscow). И клиент, и сервер считают «сейчас» и «сегодня»
    именно в нём, а не в поясе браузера.
  - Что считать прошлым для сегодняшней даты. Начало брони должно быть не раньше
    текущего момента, округлённого вверх до шага. Пример: сейчас 10:07, самое
    раннее начало — 10:15.
  - Брони, которые уже идут или прошли. Только просмотр, без редактирования и
    удаления. Удаление идущей брони можно разрешить, но я бы не стал: так
    правила проще и единообразнее.
  - Перенос брони на другую дату через PATCH. Разрешён. Проверки те же, текущая
    бронь исключается из проверки пересечений (правило 7).
  - Граница 18:00. end = 18:00 допустимо, start = 18:00 — нет: это нарушает и
    start < end, и минимальную длительность.
  - Выходные и горизонт бронирования. Ограничений нет: в спеке их нет. Упомяну
    это в README.
  - Формат ошибок:
    - 400 — некорректное тело запроса или формат данных;
    - 422 — нарушено бизнес-правило, в теле { code: "VALIDATION", errors: {
      поле: сообщение } };
    - 409 — пересечение, в теле { code: "CONFLICT", message, conflicts:
      Booking[] };
    - 404 — бронь не найдена, например удалена с другого устройства.
  - Демонстрация 409. Добавить способ вызвать 409 по запросу, например dev-флаг,
    который заставляет сервер вернуть конфликт. Иначе проверяющий не увидит
    правило 8, а без двух вкладок воспроизвести его трудно.
  - Формат отображения. Список броней плюс сетка свободных и занятых слотов. Ось
    времени на всю ширину экрана сложнее сделать доступной и адаптивной, чем
    она того стоит.

  2. Структура проекта

  Принцип: бизнес-правила — это чистые функции в одном модуле. Их импортируют и
  форма, и сервер.

  - src/domain/booking — без зависимостей от React и Next:
    - типы (Booking, BookingInput, коды ошибок);
    - утилиты времени: перевод HH:mm в минуты, генерация слотов, «сейчас» в
      часовом поясе комнаты;
    - validateBooking(input, { existing, now, excludeId }): возвращает список
      ошибок с кодами, а не текстами;
    - findConflicts: использует полуоткрытые интервалы, поэтому касание границ
      конфликтом не считается;
    - конфиг: рабочий день, шаг, минимальная и максимальная длительность,
      часовой пояс.

    Основная масса unit-тестов на граничные случаи — здесь.
  - src/server — бэкенд:
    - интерфейс BookingRepository и его реализации (in-memory и внешнее
      хранилище, см. п. 3);
    - сервисный слой createBooking, updateBooking и т. д. Он проверяет формат
      тела запроса (zod или ручная проверка), вызывает доменный validateBooking
      и атомарно проверяет пересечения при записи.
  - src/app/api/bookings/... — тонкие Route Handlers: разобрать запрос, вызвать
    сервис, перевести ошибки в HTTP-статусы. GET без кеширования. В Next 16
    params в обработчиках приходит как Promise.
  - src/lib/api — API-клиент:
    - bookingsApi.list/create/update/remove;
    - типизированные ошибки ConflictError, ValidationError, NotFoundError,
      NetworkError;
    - базовый URL настраивается.

    UI не знает ни про fetch, ни про статусы. Чтобы перейти на настоящий API,
    достаточно заменить этот модуль.
  - src/features/booking — UI:
    - хуки данных. Рекомендую TanStack Query: состояния загрузки и мутаций, а
      после 409 нужно лишь пометить список устаревшим;
    - компоненты: выбор даты, список и сетка, форма, подтверждение удаления.
  - Форма держит своё состояние отдельно от данных запроса. Поэтому повторная
    загрузка списка после 409 не сбрасывает введённое. Проверка в форме вызывает
    ту же validateBooking, а коды ошибок переводятся в тексты в одном месте.

  3. Хранилище для mock API на Vercel

  A. In-memory: переменная в модуле сервера
  - Плюсы: ничего не нужно настраивать, идеально для локальной разработки и
    тестов.
  - Минусы на Vercel:
    - у каждого экземпляра serverless-функции своя память;
    - при холодном старте данные пропадают;
    - при нескольких экземплярах устройства видят разные данные.
  - Fluid compute чаще переиспользует экземпляр, поэтому демо «иногда работает».
    Это хуже, чем «никогда»: ошибка выглядит случайной.
  - Видимость брони между устройствами не гарантирует.

  B. Upstash Redis через Vercel Marketplace (бывший Vercel KV). Рекомендую.
  - Данные хранятся постоянно и общие для всех экземпляров. Бесплатного тарифа
    хватит с запасом.
  - Ограничения:
    - нужны env-переменные, отдельно для Preview и Production;
    - REST-клиент не поддерживает WATCH, поэтому атомарную операцию «проверить
      пересечения и записать» нужно делать Lua-скриптом (EVAL) или блокировкой
      на дату (SET NX);
    - каждый запрос идёт по сети, это десятки миллисекунд;
    - в README придётся объяснить, почему используется хранилище при фразе «БД
      не нужны». Аргумент: это mock-хранилище, без него не работает требование
      видеть бронь с разных устройств.

  C. Postgres (Neon или Supabase)
  - Самая сильная гарантия: пересечения запрещаются на уровне базы (exclusion
    constraint по диапазону времени), гонок нет.
  - Минусы:
    - больше всего настройки: миграции, драйвер, пул соединений в serverless;
    - явно противоречит формулировке «БД не нужны»;
    - для 4–6 часов это перебор.

  Сразу отбрасываю:
  - MSW с localStorage: данные живут только в одном браузере, между устройствами
    их не будет;
  - Vercel Blob с JSON-файлом: нет атомарности, при одновременной записи одна
    бронь затрёт другую, плюс задержки кеша;
  - Edge Config: не предназначен для частой записи.

  Итог: один интерфейс репозитория и две реализации. In-memory — для разработки
  и тестов, Redis — когда заданы env-переменные. Выбор при старте по наличию
  env.

  4. Риски

  - Часовой пояс. Сервер в UTC, клиент в своём поясе: «прошлое время» и
    «сегодня» могут расходиться. Плюс риск ошибки гидратации, если «сейчас»
    отрисовать на сервере. Решения: один часовой пояс комнаты, «сейчас»
    вычислять на клиенте после монтирования, тесты с подставным now.
  - Гонки. Если проверку пересечений и запись делать отдельными шагами, две
    параллельные брони пройдут обе. Нужна атомарность в репозитории, иначе 409
    ненадёжен.
  - Расхождение правил клиента и сервера. Снимается одним доменным модулем.
    Сервер при этом всегда главный.
  - Потеря ввода при 409. Возникнет, если состояние формы выводится из данных
    запроса или форма закрывается при ошибке. Нужно проверить тестом.
  - Удаление или изменение брони, которую другое устройство уже удалило. Нужно
    обработать 404: понятное сообщение и перезагрузка списка.
  - Кеширование GET в Next или Vercel. Свежие брони не видны. Явно отключить
    кеш.
  - Сценарии с несколькими устройствами на Preview-деплоях без env-переменных
    молча откатятся на in-memory. Это стоит явно показывать, например в
    health-эндпоинте или в README.
  - Время. Самое затратное — доступность и адаптивность сетки слотов и UX
    ошибок. Порядок приоритетов: домен и тесты, затем API, затем базовый UI со
    всеми состояниями, потом полировка. README пишу по ходу, а не в конце.
  - Несколько агентов:
    - если агенты параллельно меняют общие файлы (типы, контракт), будут
      конфликты и расхождения;
    - каждый новый агент заново изучает контекст, это расход токенов.

  П. 3: какой риск я видел в редактировании идущей брони

  Риск в том, как это сочетается с правилом 6. Пример: бронь 10:00–11:00, сейчас
  10:20.

  - Проверка «start >= now» ломает любое изменение. Если применять её к PATCH
    буквально, пользователь не сможет даже продлить бронь до 11:30. Её начало
    10:00 уже в прошлом, и сервер отклонит запрос.
  - Без этой проверки появляется лазейка. Через редактирование можно переписать
    прошлое: перенести начало на 09:00 или сократить бронь до 10:10, то есть
    так, что она закончится в прошлом.
  - Удаление идущей брони задним числом освобождает уже прошедшее время. Для
    mock это мелочь.

  Предлагаемое правило для редактирования идущей брони. Оно живёт в
  validateBooking и передаётся через context.original:
  - начало можно оставить как было, даже если оно уже в прошлом;
  - новое начало должно быть не раньше текущего момента;
  - конец должен быть строго позже текущего момента;
  - прошедшие брони (конец уже наступил) доступны только для просмотра, как на
    клиенте, так и на сервере.

  Сама возможность редактировать идущие брони остаётся в Open questions.

  П. 6: zod и TanStack Query

  Ни то, ни другое не нужно.

  zod. Сервер должен проверить тело запроса: это объект, date в формате
  YYYY-MM-DD, start и end в формате HH:mm, title — строка не длиннее 100
  символов. Это около 30 строк функции parseBookingInput в домене. Она
  возвращает тот же тип ошибок с кодами, что и validateBooking. Без zod весь
  контракт ошибок описан в одном месте и нет второго языка описания схем.

  TanStack Query. Из его возможностей реально нужны только три:
  - состояние загрузки;
  - повторная загрузка списка после мутации или 409;
  - отмена устаревшего запроса при быстрой смене даты.

  Хватит хука useBookings(date):
  - возвращает { status: 'loading' | 'error' | 'success', data, error, reload };
  - использует AbortController, чтобы ответ на старую дату не перезаписал новую;
  - при reload держит прежний список на экране и показывает индикатор
    обновления, а не пустой экран.

  Мутации обрабатывает форма: локальный флаг submitting, после успеха или 409
  вызывается reload(). Это примерно 50 строк, и их легко протестировать. Чего мы
  лишаемся: кеша между датами, дедупликации и повторного запроса при возврате
  на вкладку. Для четырёх эндпоинтов это не нужно, и в README я так и напишу.

  Нюансы, которые стоит знать до одобрения

  - Лимиты агентов только частично технические. В .claude/agents/*.md технически
    задаются только model и tools. Размер отчёта и бюджет — это инструкции в
    промпте агента, а не жёсткое ограничение. Шаблоны Bash-команд вида npm run
    test в frontmatter агента не задать: они настраиваются в
    .claude/settings.json и действуют на всю сессию. Реальные рычаги экономии —
    узкие задания со списком файлов, модель под задачу и короткие форматы
    отчёта.
  - Часовой пояс нужен и на клиенте. Поэтому переменная окружения —
    NEXT_PUBLIC_ROOM_TZ. На сервере читается она же, источник один. В
    Asia/Bishkek (UTC+6) нет перехода на летнее время: это упрощает расчёты, но
    код на это всё равно не полагается.
  - Атомарность в in-memory. Проверка пересечений и запись выполняются
    синхронно, без await между ними. В Node этого достаточно, чтобы внутри
    одного экземпляра не было гонок. Хранилище — синглтон на globalThis, чтобы
    переживать hot reload в dev-режиме.
  - Dev-флаг для 409 должен работать и на Vercel, иначе проверяющие не увидят
    правило 8. Сервер принимает заголовок x-mock-force-conflict, только когда

  Свежие данные в GET при cacheComponents

  Проверил по документации Next 16.4 в node_modules/next/dist/docs.

  - Как это работает. С cacheComponents GET-обработчик выполняется во время
    запроса, если читает данные запроса (req.url, headers) или вызывает
    connection(). Если не читает ничего из этого, Next пререндерит его при
    сборке. Опции dynamic, revalidate и fetchCache в этом режиме удалены, так
    что запрет на них ничего не ломает: средство просто другое.
  - Наш GET читает ?date= из request.nextUrl, значит выполняется на каждом
    запросе.
  - Риск. Если после рефакторинга обработчик перестанет читать запрос (например,
    появится дата по умолчанию), Next молча пререндерит ответ из пустого
    in-memory хранилища. Список навсегда останется пустым, и ошибки при этом не
    будет.
  - Что добавил в PLAN.md, фаза 3A:
    - await connection() первой строкой GET — явный, задокументированный способ
      отключить пререндер;
    - Cache-Control: no-store во всех ответах API и cache: "no-store" на
      клиенте;
    - критерий готовности: в выводе npm run build маршрут /api/bookings помечен
      как динамический (ƒ).
